# Privacy and storage parity

Previously JSON stored and searched raw new descriptions while PostgreSQL persisted the existing secret-redacted description. The existing baseline fixture found a synthetic password in JSON search. Redaction now lives in the common ticket plan before persistence and response serialization, so both backends omit the synthetic secret from newly created records and search. Mock AI already runs its own redaction, audit detail passes the existing structured redactor, and queued workflow notifications use its existing redactor. No historical backfill took place. Searches over previously stored descriptions continue to query their stored representation. The database and HTTP parity suites cover new writes.

Free-form custom fields, titles, document bodies and historical records need an approved privacy model. Proposed model: classify fields by purpose and permitted consumers; use typed validated identifiers where workflows require exact parameters; redact secret-bearing free text before persistence, indexing and AI context; minimize notification/log fields; apply published-knowledge authorization before retrieval; require approved retention and backup policy. Secret-pattern matching alone cannot recognize all sensitive data.

If approved, inventory legacy data by record ID and exposure surface using aggregate counts, take an encrypted verified snapshot, rehearse a reversible migration on synthetic data, update derived indexes in the same rollout, and compare counts, references, audit integrity and representative search results before cutover. Rollback would restore the reviewed snapshot or reversible per-record backup under controlled access. Record how historical searches change before scheduling migration.
