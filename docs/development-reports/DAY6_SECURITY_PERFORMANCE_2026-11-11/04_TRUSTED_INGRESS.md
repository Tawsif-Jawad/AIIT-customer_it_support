# Trusted ingress

Without configuration, the peer is the immediate transport address. To enable forwarding at the API, set `API_TRUSTED_PROXY_IPS` to a comma-separated list of exact addresses, `API_PROXY_TOKEN` to a randomly generated 32–128 character URL-safe secret, and `API_PUBLIC_ORIGIN` to the canonical HTTPS origin. An explicit loopback HTTP origin supports the development harness. The trusted hop presents `X-AIIT-Ingress-Token`. Deploy identical configuration across API processes. Protect hop secrets and use TLS for non-loopback links.

The native web server strips inbound forwarding and ingress authentication headers and emits canonical `X-Forwarded-For`. Configure `WEB_API_PROXY_TOKEN` with the API hop secret. If the web server has a trusted upstream proxy, configure `WEB_TRUSTED_PROXY_IPS` and a separate `WEB_PROXY_TOKEN`. The public edge must replace incoming forwarding data before adding its own identity.

The parser canonicalizes IPv4, IPv4-mapped IPv6 and IPv6, accepts one forwarding format per request, bounds the chain at eight hops and walks right-to-left until the first untrusted hop. The supported `Forwarded` profile requires one literal `for=` address per element. Forwarded host and scheme fields do not determine the public origin or OIDC redirect. The API uses the configured origin for proxy mode and validates a loopback Host in direct mode. Tests cover contradictory and spoofed headers, missing secrets, trusted and untrusted peers, configured origin and multiple hops.

The shared limiter uses installation-keyed HMAC buckets with IPv6 /64 grouping. The PostgreSQL namespace bounds bucket rows and expired entries are incrementally deleted during traffic. A hash collision can make unrelated clients share a budget. JSON uses bounded local memory. Separate limits cover general requests and per-client and global OIDC initiation, plus per-client callbacks. Rejections include `Retry-After`. Database failures return 503 for protected traffic. Liveness remains independent.
