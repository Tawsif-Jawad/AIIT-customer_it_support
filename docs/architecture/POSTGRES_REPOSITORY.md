# PostgreSQL transactional slice — 10 November 2026

This is an explicitly constructed, isolated integration mode. `PostgresRepository` and `PostgresOutbox` accept an already configured Prisma client. They do not read a default database URL, switch application storage, start a worker, authenticate a caller or contact a transport. The HTTP API and its local mock queue still use `EnterpriseDataStore` JSON. The standalone JSON worker remains disabled.

## Transaction contract

`apps/api/src/postgres-repository.ts` implements `TicketRepository`: initial NEW ticket creation/read, comments, status transitions including escalation, pending-only approval decisions and custody acknowledgment. It reloads the current active user, role and SBU within every transaction. A future API adapter must supply the actor ID from an authenticated server-side session, never a request-body identity. Shared `canAccessTicket`, creation validation, transition policy and redaction remain the policy source. IT/CTO keep their documented organization-wide grant; employee/customer access requires requester ownership plus same SBU. Service accounts are denied interactive operations.

Business mutations, events, audit and any requester notification/job intent commit together in a Prisma SERIALIZABLE transaction. Ticket/asset mutations compare an explicit expected integer version; approval decisions compare PENDING plus version. A conflict aborts the entire operation and returns `RepositoryError('CONFLICT')`, including raw PostgreSQL serialization/deadlock SQLSTATEs wrapped by Prisma. Callers may retry a confirmed aborted operation with fresh state. There are no automatic production retries or external effects inside a transaction. Unknown infrastructure errors propagate to the future adapter, which must redact them and map them to an appropriate unavailable response. Shared validation errors retain their existing class.

Ticket numbers retain `INC|REQ-<UTC year>-<integer>` and source identifiers are untouched. A transactional counter atomically allocates above both its previous value and imported numeric suffixes (minimum 1000). It replaces the unsafe count-based allocation only inside this slice; existing JSON behavior is unchanged. The counter is a PostgreSQL integer: extreme legacy suffixes/counter exhaustion fail the transaction and need explicit owner remediation, never ID rewriting.

Status updates preserve CTO review restrictions and requester reopen routing back to IT; resolution and closure timestamps are set, and reopen clears them. Event records contain before/after states. Custody acknowledgment appends history and accepts identical repeat acknowledgments without duplicating history. This slice does not implement transfers/returns or new asset assignment.

## Schema and integrity

Additive migration `20261110000000_transactional_foundation` follows the two retained Day 2 migrations. It adds versions, `TicketCounter`, `NotificationJob`, job indexes/checks, composite requester/custodian-to-user SBU foreign keys, event actor and audit SBU references. Existing string IDs, historical metadata, attachment JSON and timestamps are retained. Existing incompatible associations cause migration/import failure; they are never repaired by dropping records. ADR-007 remains historical proposed wording; this work uses the already implemented Day 2 text compatibility foundation without approving production cutover or expanded organization policy.

SQL triggers reject update/delete of audit, ticket events and AI logs; completed approvals cannot be changed or deleted. Custody history must retain its entire ordered prefix, and assets with history cannot be deleted. Statement triggers reject truncating these historical tables. These guards do not protect against a database owner/superuser disabling triggers or changing DDL. Production requires separate migration/runtime credentials, least-privilege grants, retention/export policy and independent review. No production role or grant was provisioned.

## Durable outbox contract

Repository intents use deterministic identifiers derived from the committed operation: ticket creation ID, ticket version, approval ID or comment ID. Notification and job uniqueness prevent duplicate intent for that operation. New intents are `IN_APP_ONLY`; imported notifications are retained without enqueuing historical email or replaying it.

`PostgresOutbox.claim()` uses `FOR UPDATE SKIP LOCKED` and an atomic update, with a unique fencing token, database-time lease and attempt increment. Default lease is 30 seconds (validated range 100 ms–5 min); default attempt limit is five (DB range 1–20). Only the current unexpired token may complete or retry. Expired leases can be reclaimed until the attempt limit; exhausted leases become retained FAILED jobs and mark their notification failed. Explicit failures record a fixed safe reason and exponential backoff, capped at one hour. No raw transport errors, credentials or message contents are logged. Lease renewal, operational worker identity/authorization and queue monitoring are deferred.

`complete()` acknowledges the caller's processing result; it is not evidence of SMTP delivery. Tests invoke it as a synthetic consumer only. There is no automatic dispatcher and no external email transport here. External delivery after a crash may repeat; exactly-once delivery is not claimed. Client request idempotency after a committed-but-lost HTTP response remains future work.

## Import, comparison and recovery

The existing importer is extended, not replaced. It validates all source collections and references, adds requester/custodian SBU and OIDC-subject uniqueness checks, serializes imports with a transaction-scoped advisory lock, compares existing IDs for identical data and rolls back any conflict. The CLI still requires an explicit source, opt-in and loopback `aiit_test*` target. The library accepts an explicit client for the disposable harness; it must not be exposed as an unauthenticated endpoint.

`verifyImportedSnapshot()` runs a consistent REPEATABLE READ comparison of all fourteen source collections, exact counts, IDs and canonical SHA-256 data. It derives user role/SBU labels from validated FK mappings, normalizes top-level timestamp instants to UTC (session milliseconds become DateTime), preserves nested metadata/history/attachments, and excludes only DB-generated defaults absent from source (including version zero). It never rewrites the source. Manifest hashes are evidence of tested equality, not encrypted backups.

The existing test cluster is always created under a private temporary directory on loopback and ignores externally supplied target URLs. Tests apply all three migrations, repeat/concurrent import, reject conflicts after earlier inserts, compare canonical checksums, restore the imported snapshot with `pg_dump`/`psql`, and separately dump/restore every repository table after mutations, including job states and versions. A populated UUID baseline upgrade and Prisma schema parity remain verified. No operational dataset is imported or backed up by this test.

Before any future cutover: obtain explicit authorization, resolve incompatible source associations, freeze writers, preserve a restricted immutable original and verified backup, import/compare a fresh snapshot, wire all API/auth/worker operations to one authority, and pass hosted checks/review. Rollback before cutover means discarding only the disposable target. After cutover, stop writes and reconcile DB-only changes before switching back; never overwrite newer records with an old JSON snapshot.

## Remaining integration

Initial ticket creation stops at NEW; existing mock AI triage, routing/approval generation, complete recipient rules and queue processing remain in the JSON API. This is not a drop-in store replacement. User/role/SBU/catalog administration, session issuance/revocation, KB queries, attachment creation, asset transfer, separate public audit APIs and all remaining HTTP list/detail/aggregate operations need database adapters and tests. Imported tables support those records but are not complete operational repositories. No OIDC/AD/SMTP provisioning, default-mode change or production readiness is claimed.
